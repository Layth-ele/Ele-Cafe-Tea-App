## Phase 0 — Telemetry & Baselines · Week 0

> **Principle:** you cannot improve what you cannot measure. This phase is the only one that's mandatory-first. Every later phase has a metric this phase makes visible.

### 0.1 Real-User Monitoring (RUM) for Web Vitals

**What:** ship a tiny script that streams INP, LCP, CLS, FCP, TTFB per route from real users to a dashboard. Don't trust Lighthouse CI as a proxy for user experience — Lighthouse runs on a simulated 4G connection on a perfectly clean machine; your users are on subway wifi with 17 Chrome extensions.

**How:**

```bash
pnpm add web-vitals
```

```ts
// src/lib/rum.ts
import { onCLS, onINP, onLCP, onFCP, onTTFB } from 'web-vitals/attribution';

const send = (metric: any) => {
  // Beacon API: survives page unload; doesn't block.
  navigator.sendBeacon('/api/rum', JSON.stringify({
    name:        metric.name,
    value:       metric.value,
    rating:      metric.rating,
    delta:       metric.delta,
    id:          metric.id,
    navType:     metric.navigationType,
    route:       location.pathname.replace(/\/[a-z0-9]{20,}/g, '/:id'), // collapse IDs
    attribution: metric.attribution,         // explains *why* (element, event)
    deviceMemory: (navigator as any).deviceMemory,
    connection:  (navigator as any).connection?.effectiveType,
    sessionId:   sessionStorage.getItem('rum-sid') ?? crypto.randomUUID(),
  }));
};

export function initRUM() {
  if (!('sendBeacon' in navigator)) return;
  if (sessionStorage.getItem('rum-sid') === null) {
    sessionStorage.setItem('rum-sid', crypto.randomUUID());
  }
  onCLS(send);  onINP(send);  onLCP(send);  onFCP(send);  onTTFB(send);
}
```

Wire it into `main.tsx` after React mounts. Build a Cloud Function `/api/rum` that writes to Firestore (or BigQuery if you can). Build a Looker / Datastudio / simple Firebase Studio dashboard showing P50/P75/P95 by route, by device, by connection.

**Definition of done:**
- A live dashboard URL.
- A Slack alert when P75 INP on `/checkout` exceeds 250 ms over a 1-hour window.
- The route-collapsing regex catches at least `/tea-profile/:cat/:slug`, `/products/:cat`, and `/admin/products/:id`.

**Why first:** Phase 8's "improve INP" needs Phase 0's INP baseline.

### 0.2 Error tracking (Sentry / GlitchTip)

**What:** capture every uncaught error, every Promise rejection, every React render error from real users. Today errors only become visible when a customer calls support.

**How:** Sentry is the easiest, GlitchTip is the open-source/self-hosted alternative.

```bash
pnpm add @sentry/react
```

```ts
// src/lib/sentry.ts
import * as Sentry from '@sentry/react';

export function initSentry() {
  if (!import.meta.env.VITE_SENTRY_DSN) return;
  Sentry.init({
    dsn: import.meta.env.VITE_SENTRY_DSN,
    environment: import.meta.env.MODE,
    release: import.meta.env.VITE_APP_VERSION,
    integrations: [
      Sentry.reactRouterV7BrowserTracingIntegration({
        useEffect, useLocation, useNavigationType,
        createRoutesFromChildren, matchRoutes,
      }),
      Sentry.replayIntegration({
        maskAllText: false,           // tea names, prices are not PII
        maskAllInputs: true,          // emails, addresses, payment ARE PII
        blockAllMedia: false,
      }),
    ],
    tracesSampleRate: 0.1,            // 10% of transactions
    replaysSessionSampleRate: 0.05,   // 5% of sessions
    replaysOnErrorSampleRate: 1.0,    // 100% of errored sessions
  });
}
```

Hook it into `ErrorBoundary.tsx` so React render errors surface with the component tree. Configure source-map upload in the Vite build step.

**Definition of done:**
- An error from production reaches the dashboard within 30 s.
- Source maps resolve to original TSX line numbers.
- A Slack channel receives critical errors.
- Replay is stripped of PII (test by signing up with `test@example.com` and checking the replay redacts the email field).

### 0.4 Auth fixture for Playwright (unblocks visual + a11y on 14+ routes)

**What:** the visual and a11y test suites currently exclude `/checkout`, `/orders`, `/account`, and the entire `/admin/*` tree. These are the *highest-risk* parts of the app — payment, customer data, admin actions — and they have **zero** automated coverage.

**How:** mint a custom token via Firebase Admin SDK in the Playwright global-setup hook, then sign in once, persist `storageState`, reuse across tests.

```ts
// playwright.setup.ts
import { chromium } from '@playwright/test';
import { signInWithCustomToken } from 'firebase/auth';
import { initializeApp } from 'firebase/app';
import { getAuth } from 'firebase/auth';
// generate the token via a Cloud Function exposed only when NODE_ENV=test

const TEST_USER_UID  = 'playwright-test-user';
const TEST_ADMIN_UID = 'playwright-test-admin';

async function authState(uid: string, file: string) {
  const browser = await chromium.launch();
  const context = await browser.newContext();
  const page    = await context.newPage();

  // 1. Hit a /test-login route that mints a custom token server-side.
  //    Cloud Function gates by env: only mints when FIREBASE_PROJECT_ID
  //    matches a known TEST project.
  const token = await fetch(`${BASE_URL}/api/test-login?uid=${uid}`)
    .then(r => r.text());

  // 2. Inject and sign in via Firebase JS SDK.
  await page.goto('/');
  await page.evaluate(async (token) => {
    const { signInWithCustomToken } = await import('firebase/auth');
    const { auth } = await import('/src/lib/firebase');
    await signInWithCustomToken(auth, token);
  }, token);

  // 3. Persist storageState (cookies + localStorage with auth token).
  await context.storageState({ path: file });
  await browser.close();
}

export default async function globalSetup() {
  await authState(TEST_USER_UID,  'tests/.auth/user.json');
  await authState(TEST_ADMIN_UID, 'tests/.auth/admin.json');
}
```

Then extend `playwright.config.ts` projects so the user-state and admin-state projects run with `storageState` pointed at those files. Add the protected and admin pages to `tests/visual/public-pages.spec.ts` and `tests/a11y/public-pages.spec.ts`.

**Definition of done:**
- 28 baselines → ~80 (adds `/checkout`, `/orders`, `/account`, all 7 admin pages × 2 themes × 2 viewports).
- A11y suite covers every route, exits 0.
- `tests/.auth/*.json` is gitignored; CI generates it via the global-setup.
- The `setAdminRole` callable function gates by env so only the test project can mint admin claims.

## Phase 1 — Design Tokens v3 · Week 1

> Your `tokens.css` is already best-in-class for color and surface. This phase adds the missing tiers and migrates color to a perceptually-uniform space.

### 1.1 Migrate colors to OKLCH (perceptual uniformity)

**Why:** sRGB hex is non-uniform — `#888888` is not perceptually halfway between black and white; midtones bunch up. OKLCH (Oklab + chroma + hue) **is** uniform: tweaking lightness by 0.05 produces a visually equal step everywhere on the wheel. Browsers shipped support in 2023; it's safe today.

**The non-obvious payoff** is automated palette generation. With OKLCH you can do:

```css
--gold-500: oklch(74% 0.13 75);
--gold-600: oklch(64% 0.13 75);  /* same hue, same chroma, -10% lightness */
--gold-700: oklch(54% 0.13 75);
```

…and the steps look right. With hex you eyeball every step and they drift. The `tokens.css` `_gold-200` → `_gold-800` ladder is a perfect candidate for re-derivation.

**How:**

1. Pick a color-pair generator (`oklch.com`, `huetone`, `Leonardo` from Adobe). Re-derive your `_ink-*`, `_cream-*`, `_gold-*` private palettes from a base hue + chroma + lightness ladder.
2. Use a `@supports` fallback for the (rare) browsers that don't do OKLCH:

```css
:root {
  --gold-500: #b8924a;                      /* sRGB fallback */
  --gold-500: oklch(64% 0.10 75);          /* OKLCH (overrides if supported) */
}
```

3. Use `color-mix()` for systematic transparency:

```css
/* before */
--gold-50: rgba(184, 146, 74, 0.05);
/* after — systematically derived from --gold-500 */
--gold-50: color-mix(in oklab, var(--gold-500) 5%, transparent);
```

4. Validate contrast. Run a script that loops your foreground / background pairs and asserts ≥ 4.5:1 for normal text, ≥ 3:1 for large text and UI components. Tool: `culori` (npm).

**Definition of done:**
- All `_gold-*`, `_ink-*`, `_cream-*` ladders use OKLCH with sRGB fallback.
- Visual regression suite passes (re-baseline once, intentionally).
- Contrast script in CI; fails on any pair below 4.5:1 for body text.

### 1.2 Motion tokens

Your `design.css` has motion strings sprinkled in component classes. Pull them up:

```css
:root {
  /* Durations — three tiers: micro, macro, expressive. */
  --d-1: 100ms;     /* hover state, focus ring fade */
  --d-2: 200ms;     /* button press, toggle, expand */
  --d-3: 300ms;     /* drawer, popover */
  --d-4: 450ms;     /* modal, page section reveal */
  --d-5: 600ms;     /* route transition, hero animation */

  /* Easings — purpose-named, not "ease-out-quad". */
  --ease-standard:  cubic-bezier(0.2, 0.0, 0.0, 1.0);   /* most things */
  --ease-emphasized: cubic-bezier(0.3, 0.0, 0.0, 1.0);  /* hero, large surfaces */
  --ease-decelerate: cubic-bezier(0.0, 0.0, 0.0, 1.0);  /* exits, dismissals */
  --ease-spring:     cubic-bezier(0.34, 1.2, 0.64, 1);  /* playful entrance — your modal already uses this */

  /* Distances — how far things move. */
  --dist-sm: 4px;
  --dist-md: 16px;
  --dist-lg: 32px;
}

@media (prefers-reduced-motion: reduce) {
  :root {
    --d-1: 1ms;  --d-2: 1ms;  --d-3: 1ms;
    --d-4: 1ms;  --d-5: 1ms;
    --ease-standard: linear;
    --ease-emphasized: linear;
    --ease-decelerate: linear;
    --ease-spring: linear;
  }
}
```

Now `design.css` rules look like:

```css
.btn {
  transition: background-color var(--d-2) var(--ease-standard),
              color var(--d-2) var(--ease-standard),
              transform var(--d-1) var(--ease-decelerate);
}
```

…and reduced-motion is automatic.

## Phase 3 — Inline-Style Migration · Week 3

> 1,590 inline `style={{}}` instances → ~50 (the legitimate dynamic ones). Builds on `PHASE_3_PLAYBOOK.md`. Speed comes from codemods, not hand-editing.

### 3.1 The codemod approach

Hand-migrating 1,590 instances at 2 minutes each = 53 hours of monkey work. Don't do it. Write a [jscodeshift](https://github.com/facebook/jscodeshift) transform that:

1. Walks every `.tsx` file.
2. Finds JSX `style={{...}}` attributes where every property value is either a string literal, a number literal, or a `var(--...)` call (not a JS variable).
3. Hashes the static style object → generates a CSS class name.
4. Emits the class in a generated `src/styles/_generated.css` file (one file per source file, e.g. `_generated/HomePage.css`).
5. Replaces the JSX `style={{...}}` with `className={...}`.
6. Adds the import.

Run the codemod, run visual regression — if all 28 baselines (now 80 after Phase 0) match, the migration was correct. If a few don't match, the codemod missed an edge case; fix the codemod and re-run, don't hand-fix.

### 3.2 Bucketing

The codemod will leave behind two categories:

| Bucket | Count (estimated) | Action |
|---|---|---|
| **Static** (just literals + var()) | ~1,000 | Codemod handles; emit class |
| **Mixed-static** (literals + 1-2 dynamic) | ~400 | Codemod emits a class for static parts, keeps `style={{ width: pct }}` for the dynamic part |
| **Truly dynamic** (computed every render) | ~200 | Convert to CSS custom property: `style={{ '--w': pct }}` and use `width: var(--w)` in CSS |

After the codemod, ESLint's `react/forbid-dom-props` rule (currently warn) flips to **error**. Now no new inline styles can land.

### 3.3 Order of attack

Do it page-by-page so visual regression catches drift one page at a time:

1. `HomePage.tsx` (393 lines, hot path, baseline exists)
2. `ProductsPage.tsx` (752 lines, hot path, baseline exists)
3. `TeaProfilePage.tsx` (1004 lines, hot path, baseline exists)

### 3.4 Bundle expectations

Pass 7 of `FIXES_CLAUDE_AUDIT` shaved ~46 kB by removing 30 npm packages. Phase 3 should shave another 30–60 kB by:

## Phase 5 — States Library · Week 5

> Three states, one good UI. The bad UI shows three states (default, loading, success) and forgets the other six (empty, partial-loading, error, retry, permission, offline, stale, optimistic, conflict). Inventory every async path; pattern every state.

### 5.1 The taxonomy

| State | When | Pattern |
|---|---|---|
| **Initial** | First load, no data, no interaction | Skeleton matching final shape, not a spinner |
| **Loading** | After interaction, awaiting result | Inline progress on the affected element only — never a full-screen spinner over good content |
| **Optimistic** | Local change before server confirms | Render as success immediately; mark `aria-busy`; rollback on error with toast undo |
| **Empty** | Loaded successfully, zero results | Helpful message + CTA + maybe illustration |
| **Partial empty** | Loaded but filter excludes all | "No teas match these filters" + "Clear filters" button |
| **Error — network** | Fetch failed | Toast + inline retry button; preserves any in-progress input |
| **Error — validation** | User input rejected | Inline at field; never a toast |
| **Error — permission** | User can't see this | Friendly message + login link + "go home" |
| **Error — not found** | Entity doesn't exist | 404 page with search and recent links |
| **Offline** | Network down | Banner + cached content + "you're offline" indicator |
| **Stale** | Data is N seconds old (Tanstack Query gives you this) | Subtle — gray dot, "updating…" text |
| **Conflict** | Two writes raced | Show both versions, ask user to pick (rare for this app — only relevant in admin multi-user) |

### 5.2 Skeleton-by-shape (not skeleton-everywhere)

A spinner is a *shrug*. A skeleton is a *promise*. The skeleton should match the shape of what's coming: card-skeleton for cards, line-skeleton for text, table-skeleton for tables. You have a `Skeleton` primitive — extend with shape variants and use it everywhere data loads.

```tsx
<Skeleton.Card />          // 240×320 with image + title + price
<Skeleton.Line w="60%" />  // a single line
<Skeleton.Avatar />        // 40×40 round
<Skeleton.Table rows={5} cols={4} />
```

Use `Suspense` boundaries wrapping each lazy route + each data-fetching island, with the right skeleton. Today you `Suspense fallback={null}` in `App.tsx` — that's a missed opportunity for free perceived-perf wins.

### 5.3 Optimistic UI patterns

The cart is the obvious place. Today (`useCart`) is a Zustand store; sync to Firestore happens via `useCartSync`. Today's pattern:

1. Click "Add to cart"
2. Local store updates
3. Sync writes to Firestore
4. (If sync fails: silent? The user thinks it worked.)

Better:

1. Click "Add to cart"
2. Local store updates immediately (✓ optimistic)
3. Sync writes
4. On success: toast "Added" with undo
5. On failure: rollback local store, toast "Couldn't add — try again"

Tanstack Query's `useMutation` has built-in optimistic update support: `onMutate` updates the cache, `onError` reverts, `onSettled` invalidates. Adopt the pattern uniformly.

### 5.4 Error recovery

Every error toast offers a **retry**. Every error page offers a **way out** (back home, contact support, account login). Never a dead end.

### 6.2 Validation timing rules

Universal rules:

- **First-pass:** validate `onBlur`. Don't yell at users while they're typing.
- **After first error on a field:** flip to `onChange` for that field only. As soon as it's valid, stop nagging.
- **On submit:** validate everything, scroll to first error, focus it.
- **Async validation** (e.g. "is this email taken"): debounce 400 ms, render a quiet "checking…" state, never block submit on it.

RHF's `mode: 'onTouched'` + `reValidateMode: 'onChange'` gets you the first three for free.

### 6.3 Field primitives

Build:

```tsx
<Field>

  <Field.Hint>{t('We use this for order updates only.')}</Field.Hint>

  <Field.Error>{errors.email?.message}</Field.Error>
</Field>
```

`<Field>` handles: `id` generation, `aria-describedby` wiring (label + hint + error), error styling, label/input association. This single component fixes all ~50 of the missing-`htmlFor` violations Phase 0.5 surfaces.

### 6.4 Autofill & autocomplete attributes

The single best UX win in form-land. The browser knows the user's email, address, card details — let it fill them. Audit every input for the right `autocomplete` attribute:

- `email` (login, signup, checkout)
- `current-password` (login)
- `new-password` (signup, password reset)
- `name`, `given-name`, `family-name` (signup, checkout)
- `street-address`, `address-line1`, `address-line2`, `address-level1` (state), `address-level2` (city), `postal-code`, `country` (checkout shipping)
- `tel`, `tel-national` (contact, account)
- `cc-number`, `cc-name`, `cc-exp`, `cc-csc` (payment — but you delegate to a payment provider, so verify their form has these)
- `one-time-code` (verification SMS — Safari iOS auto-fills from SMS)
- `off` only when you really mean it

Cuts checkout completion time by ~30 seconds on mobile (industry data).

### 6.5 Multi-step pattern

`CheckoutPage` (1194 lines) is one big page. The gift-builder is multi-step. Standardize:

- Progress indicator (steps with current highlighted)
- Each step independently validates; can't advance without
- Back button preserves state (don't lose entered data)
- Browser back button preserves state (URL hash for step + sessionStorage for data)
- Skip to confirm if all data is filled (return user)

### 6.6 Submit-state pattern

Every submit button:

```tsx
<Button type="submit" disabled={isSubmitting} aria-busy={isSubmitting}>
  {isSubmitting ? <Spinner /> : null}

</Button>
```

`aria-busy` so screen readers know. Disable so double-submit is impossible. Don't disable too eagerly (only after the click — if you disable it pre-click on form-invalid, the user can't tell why).

```tsx
    sizes="(min-width: 768px) 50vw, 100vw"
    loading={priority ? 'eager' : 'lazy'}
    fetchpriority={priority ? 'high' : 'auto'}
    decoding="async"
    alt={alt}
    width={400}
    height={533}
    style={{ background: blurhashDataUrl }}
  />
</picture>
```

### 8.5 INP optimization

## Phase 9 — Mobile-First & Cross-Device · Week 9

### 9.1 Container queries

Pass 3's "12 different breakpoints" finding still has 12 ad-hoc values. The deeper problem is that media queries gate on viewport, but components live in containers — a card that wants to switch from row to column at 400px wide doesn't care if the viewport is 400px or 1200px; it cares about its own container.

Container queries (shipped in all evergreen browsers since 2023):

```css
.product-card-container {
  container-type: inline-size;
  container-name: product-card;
}

@container product-card (min-width: 320px) {
  .product-card { display: grid; grid-template-columns: 1fr 1fr; }
}
```

Migrate each component that has internal layout breakpoints from `@media` to `@container`. The 12 ad-hoc breakpoint values shrink to 5 viewport-level + N component-level (which is fine because they're scoped).

### 9.2 Safe-area insets (notched devices)

iPhone notches eat content. CSS env() variables expose the safe area:

```css
.page-shell {
  padding-top:    max(env(safe-area-inset-top), 16px);
  padding-bottom: max(env(safe-area-inset-bottom), 16px);
  padding-left:   max(env(safe-area-inset-left), 16px);
  padding-right:  max(env(safe-area-inset-right), 16px);
}

/* Sticky bottom button respects iOS home indicator */
.sticky-cta {
  bottom: env(safe-area-inset-bottom, 0);
}
```

Audit every fixed/sticky element. Audit every modal bottom-edge. Pass 3 already did `100dvh`; this is the next layer.

### 9.3 Gesture support

Mobile users expect:

- Swipe-to-dismiss on drawers and bottom sheets (your `CartDrawer` doesn't support it today).
- Pull-to-refresh on top-level lists (`/products`, `/orders`).
- Long-press for contextual actions (admin tables — cmd+click on desktop, long-press on mobile).

Library: `@use-gesture/react` for primitives + `framer-motion` for the animation, OR roll yourself with PointerEvent. Use the same gesture system across the app for consistency.

### 9.4 PWA install prompt

`beforeinstallprompt` event. Customize the UX — your default "install" badge in the URL bar is ignored. Show a tasteful prompt after the user has had a successful purchase (high-intent moment).

```tsx
window.addEventListener('beforeinstallprompt', e => {
  e.preventDefault();
  setInstallPrompt(e);
});

// Later, on a high-intent moment:
if (installPrompt && !installedRecently()) {
  showCustomInstallBanner({ onAccept: () => installPrompt.prompt() });
}
```

### 9.5 Web Share Target

Once installed, the PWA can be a share target — users hitting "share" on a tea blog post can send the URL to your app, which auto-opens a search. Configure in `manifest.webmanifest`:

```json
{
  "share_target": {
    "action": "/share",
    "method": "GET",
    "params": { "title": "title", "text": "text", "url": "url" }
  }
}
```

Build a `/share` route that takes the URL, parses, searches, redirects. Underrated nicety.

### 9.6 Tablet / iPad audit

The forgotten breakpoint. Run every page at 768×1024 portrait + 1024×768 landscape. Common issues:

- 2-column layouts that should be 3.
- Mobile nav that should be desktop nav.
- Modals that go full-screen on mobile but not on tablet (often wrong — tablet should have centered modals like desktop).

## Phase 10 — Microinteractions & Motion System · Week 10

> Phase 1.2 added motion tokens; Phase 4.5 added view transitions; this phase pulls them into a coherent system.

### 10.1 Motion principles

A short doc anyone can reference:

1. **Motion serves meaning.** A drawer slides from where it'll live (right edge → from right). A toast comes in from where the eye should track (top-right → corner). A card expanding from its position uses FLIP, not a generic fade.
2. **Duration scales with distance.** Small moves use `--d-1` (100ms). Big moves use `--d-4` (450ms). No animation longer than 600ms (after that, the user is waiting on you).
3. **Easing scales with personality.** `--ease-standard` is neutral. `--ease-spring` is playful (modal open). `--ease-decelerate` is dismissive (modal close, drawer dismiss).
4. **Reduced-motion is real.** Phase 1.2's `@media (prefers-reduced-motion: reduce)` collapses durations to 1ms; that's the default. Don't `transform: scale(...)` even with `--d-1: 1ms` — make the scale itself conditional.
5. **The element doing the work isn't the element being animated.** Animate `transform` and `opacity` only — these are GPU-cheap. Layout-affecting properties (`width`, `padding`, `top`) cause re-flow.

### 10.2 FLIP animations

For "this card moves from grid position A to grid position B" (e.g. when you sort a product list), use FLIP — First, Last, Invert, Play. `react-flip-toolkit` or roll yourself. Cheap, beautiful, native.

### 10.3 Choreographed entrance

`/` (HomePage) hero section can entrance-animate on first paint. Stagger sub-elements:

```css
@keyframes hero-rise {
  from { opacity: 0; transform: translateY(8px); }
  to   { opacity: 1; transform: translateY(0); }
}
.hero-title    { animation: hero-rise var(--d-4) var(--ease-emphasized)   0ms forwards; }
.hero-subtitle { animation: hero-rise var(--d-4) var(--ease-emphasized)  60ms forwards; }
.hero-cta      { animation: hero-rise var(--d-4) var(--ease-emphasized) 120ms forwards; }
```

NB: only on first paint — if the user is returning from a `back` navigation, the hero shouldn't replay (use `view-transition-name` to keep continuity).

### 10.4 State micro-animations

- Buttons: 80ms scale-down on press (`transform: scale(0.97)`), 120ms back. iOS-native feel.
- Toggles: 200ms cross-fade between checked/unchecked states; 200ms shift of the thumb.
- Adding to cart: a small "+1" floats from the button to the cart icon, then the cart icon bumps. Wins joy.
- Form success: a 150ms green check pulse on the field. Don't celebrate every small thing — pick the moments.
- Form error: a 200ms shake on the field, then the error appears. Subtle.

### 10.5 Phase 10 success gate

- [ ] `MOTION_GUIDE.md` published with the principles + the tokens.
- [ ] All animations use motion tokens, not inline durations.
- [ ] FLIP on product grid sort/filter.
- [ ] Hero choreography on first paint, suppressed on re-entry.
- [ ] Reduced-motion path tested for every animation.

## Phase 12 — Continuous Quality Governance · Week 12

> The point isn't to ship a polished UI; it's to make polished UI the cheapest path. After 11 weeks of investment, the system *prevents regression* on every PR. This phase formalizes that.

### 12.1 PR review checklists

Two checklists, each a GitHub PR template. The author ticks; the reviewer verifies.

**UI/CSS PR checklist:**

```markdown
- [ ] No new inline `style={{}}` (lint enforced — confirm 0 new warnings)
- [ ] No new hex / `transition: all` / raw color (stylelint enforced)
- [ ] Affected pages re-baselined in visual regression OR diff is intentional
- [ ] Affected components updated in Storybook
- [ ] Chromatic approved
- [ ] Light + dark + forced-colors visually verified
- [ ] Reduced-motion still works
- [ ] Touch targets ≥ 44×44 on every interactive
- [ ] Focus visible on every interactive
- [ ] Keyboard-only flow tested
```

**Component PR checklist (anything in `src/app/components/ui/`):**

```markdown
- [ ] Storybook story added/updated, all variants
- [ ] Chromatic approved
- [ ] A11y panel green
- [ ] Token system used (no hex, no magic numbers)
- [ ] Props typed; required vs optional explicit
- [ ] forwardRef where DOM access matters
- [ ] Polymorphic via `asChild` if it makes sense
```

### 12.2 Feature flags

```bash
pnpm add @growthbook/growthbook-react
```

(Or LaunchDarkly, Statsig, ConfigCat — pick one.) Wire the SDK; gate experimental features behind flags. Now Phase 11.4 wishlist can ship behind `feature.wishlist`, only enabled for 5% of users for a week, watched in RUM + Sentry, before global rollout.

### 12.3 A/B test framework

Same SDK does it. Define: hypothesis, primary metric, MDE, duration, winning criterion. Don't run an experiment without those four. The "every change is an A/B test" cargo cult is more trouble than it's worth — only test high-impact changes.

### 12.4 Quarterly UX audit cadence

Every 3 months, one engineer + one designer do a 1-day sweep:

- Top 5 task flows: time them, count clicks, identify friction.
- New competitive review (3 competitor sites).
- RUM dashboard review: any P75 regression > 10%?
- Sentry top-error review: any new patterns?
- Any user feedback themes?

Publish: a 1-page memo with 3 fixes for next quarter. No more, no less.

### 12.5 Customer feedback loop

- Intercept survey on order confirmation: 2 questions (NPS + open-text).
- 30-day post-purchase email: "How's the tea? Anything we could do better?"
- In-app feedback widget on every page (small, dismissable).
- Feed responses into a Notion / Linear queue. Weekly triage.

### 12.6 Definition of "shipped"

For any UI feature:

1. Storybook story exists with all variants.
2. Chromatic approved by design.
3. Visual regression baselines updated (if affecting public pages).
4. A11y test passing on the affected route.
5. Lighthouse CI passing on the affected route.
6. Bundle size delta within budget.
7. RUM showing no P75 regression after 24h.
8. Sentry showing no new error spike.
9. PR checklist ticked.

Anything less is "merged," not "shipped."
