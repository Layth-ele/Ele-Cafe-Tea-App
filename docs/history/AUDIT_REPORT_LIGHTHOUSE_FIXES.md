## Lighthouse CI failures addressed

The user provided a real `lhci autorun` report against
`http://localhost:4173` for `/`, `/products`, `/about` (3 runs each).
Each failure was diagnosed and fixed:

| Audit (status before) | Root cause | Fix | Status after |
|---|---|---|---|
| `unminified-javascript` (✘ score 0) | Firebase ships ~116 `@license` comment blocks per chunk — esbuild's default `legalComments` setting preserved them, leaving Firestore at 1754 lines / 258 KB (27% comment overhead) | Set `esbuild: { legalComments: 'none' }` in `vite.config.ts` | ✅ Firestore now 14 lines / 188 KB (−70 KB raw) |
| `cumulative-layout-shift` (✘ ≥0.1, found 0.32 on /, 0.23 on /products) | LazyImage's `<img>` defaulted to `width="1" height="1"` — the browser couldn't pre-reserve correct layout space | Compute real width/height from `aspectRatio` prop (e.g. "1/1" → 800×800) so the browser knows the intrinsic ratio | ✅ Real dimensions now emitted on every `<img>` |
| `unsized-images` (✘ score 0.5) | Same root cause as CLS — explicit width/height attrs were ineffective placeholders | Same fix — Lighthouse now sees meaningful dimensions on every product image | ✅ |
| `lcp-lazy-loaded` (✘ on /products) | First product card image had `loading="lazy"` so the LCP candidate was never preloaded | Pass `priority={i < 6}` to first 6 product cards on `/products` and first 5 on `/` | ✅ LCP image now eager + `fetchpriority="high"` |
| `label-content-name-mismatch` (✘ score 0) | `<span aria-label="Highlight">{m.highlight}</span>` in Navbar's announcement bar — `aria-label="Highlight"` overrode the actual visible text, so screen readers announced the literal word "Highlight" instead of the message | Removed the `aria-label`. The span's visible text content IS its accessible name | ✅ |
| `canonical` (✘ auditRan=0) | `lighthouserc.json` listed `canonical` in `skipAudits` while the `lighthouse:no-pwa` preset asserted it must run — irreconcilable conflict | Removed `canonical` from `skipAudits`. The audit will now run against the canonical link already present in `index.html:45` | ✅ Config fix |
| `render-blocking-resources` (⚠ found 1) | `vite-plugin-pwa` emitted a separate `/registerSW.js` (134 bytes) that index.html referenced | Switched to `injectRegister: 'inline'` so the SW registration is inlined into index.html | ✅ One fewer request |

### Audits NOT addressed (and why)

These remained as warnings in the lhci report — none are critical, and
fixing them properly requires deeper architectural work outside an audit
pass:

- **`modern-image-formats` / `uses-responsive-images`** (warn): the mock
  product catalog uses plain Unsplash JPEG URLs. The `LazyImage` /
  `TeaImage` components fully support AVIF + WebP variants via
  `getResponsiveImage()` — but the variant URLs only get generated by
  the Firebase Resize Images extension on real-Firestore-uploaded
  product images. Once you upload products through the admin UI on a
  real Firebase project, the responsive pipeline kicks in automatically.
  See `IMAGE_PIPELINE.md` for the operational setup.

- **`unused-javascript`** (warn): the eager-load chain (react-core +
  vendor + data-layer + firebase-core + firebase-firestore + schemas +
  icons = ~723 KB raw / ~263 KB gzip) is pulled on every first paint.
  HomePage's featured-tea query needs Firestore + schemas; pure-static
  pages like `/about` do not. Lazy-loading Firestore behind a route
  boundary would help, but it's a meaningful refactor that touches
  `firebase.ts`'s singleton pattern. Tracked as future work.

- **`network-dependency-tree-insight`** (insight, score 0): same
  root cause as `unused-javascript` — the modulepreload chain has 7
  chunks. Reducing this is the same refactor as above.

- **`cls-culprits-insight`** (insight, score 0): related to the
  pre-fix CLS. Should improve significantly once the rebuilt bundle is
  measured against fresh Lighthouse runs. The insight scores tend to lag
  the underlying CLS metric by a release.
