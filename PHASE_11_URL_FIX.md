## The URL bug — what broke and what's fixed

### Symptom

`https://elecafe.ca/tea-profile/black/monk's-blend` did not open the Monk's Blend page reliably. In markdown renderers the link split at the apostrophe (rendering as `[monk](/tea-profile/black/monk)'s-blend`). On the actual site, behavior depended on whether the database slug matched the URL exactly.

### Root causes (multiple, fixed independently)

**1. Five link generators sidestepped the slug normalizer.** `HomePage.tsx` (3 sites), `RelatedTeas.tsx`, and the `getSitemap` Cloud Function all did `\`/tea-profile/${cat}/${slug}\`` raw string concat. If a DB slug had drifted from canonical form, every link from those pages emitted the non-canonical form, propagating the problem.

**2. `canonicalUrl` on TeaProfilePage** (used for `og:url` + `rel="canonical"`) used the raw `product.slug` — so even if a user typed the canonical URL, the SEO meta told search engines the page's canonical URL was the non-canonical form. Bad for indexing.

**3. No migration path for non-canonical slugs already in the database.** If tea documents have drifted slugs (`monk's-blend`, `Earl Grey`, etc), no script existed to find or fix them.

### Fixes shipped

| Layer | Change |
|---|---|
| **Link generators** | `HomePage`, `RelatedTeas` now use `ROUTES.TEA_PROFILE(cat, toSlug(slug))` or `encodeURIComponent(toSlug(slug))` — every link rendered passes through the canonicalizer regardless of DB state |
| **Structured-data JSON-LD** | `HomePage` itemList URL now `toSlug`-encoded |
| **TeaProfilePage canonical** | `canonicalUrl` (for `og:url` + `rel=canonical`) now `toSlug(product.slug)` |
| **Sitemap CF** | `getSitemap` in `functions/src/index.ts` canonicalizes each tea URL at emit time using a local `canonicalSlug()` mirror of `toSlug` |
| **Migration script** | `scripts/migrate-non-canonical-slugs.mjs` — reads `/teas`, finds any non-canonical slug field or doc id, reports them, optionally applies `slug` field updates (doc id renames remain manual) |
| **Vitest regression suite** | `tests/unit/lib/slugify.test.ts` already covered 18 cases including the exact `Monk's Blend → monks-blend` case |

### Run the migration

```bash
# Dry-run first
node scripts/migrate-non-canonical-slugs.mjs

# Output looks like:
#   Found 2 mismatch(es):
#     [non-canonical] doc id="monk-blend"  current="monk's-blend"  canonical="monks-blend"
#     [non-canonical-docid] doc id="Earl-Grey"  current="Earl-Grey"  canonical="earl-grey"

# Apply slug-field fixes (doc-id renames stay manual)
node scripts/migrate-non-canonical-slugs.mjs --apply
```

After this runs, every `/teas/*` document has a canonical slug field, every link generated by the app is canonical, every URL in the sitemap is canonical, and the redirect machinery in `TeaProfilePage` keeps non-canonical-pasted URLs working forever.

### What landed this turn

#### 1. HomePage `<RecentlyViewedSection>` placement

`src/app/pages/HomePage.tsx` — `<RecentlyViewedSection heading="Pick up where you left off" limit={6}>` slotted between the Featured Teas grid and the Eight Collections section. Renders null for first-time visitors (no entries in store) so it doesn't add clutter for new users. Returning visitors see their last 6 viewed teas.

#### 2. CF `userAcceptsCategory` integration via `sendEmail` gate

`functions/src/lib/notificationPrefs.ts` already exposed `userAcceptsCategory()` and `filterUidsByCategory()` — but no Cloud Function ever called them. **Fixed by injecting the gate into the universal `sendEmail()` function** rather than asking every individual function to remember.

```typescript
// functions/src/index.ts — sendEmail() now accepts optional uid + category
async function sendEmail(opts: {
  to: string;
  subject: string;
  html: string;
  uid?: string;
  category?: NotificationCategory;
  // ...
}) {
  // Phase 11.5 — gate. Bypass if uid OR category omitted
  // (covers transactional auth emails where opt-out isn't valid).
  if (opts.uid && opts.category) {
    const accepts = await userAcceptsCategory(opts.uid, opts.category);
    if (!accepts) {
      console.log(`[sendEmail] suppressed (uid=${opts.uid} opted out of ${opts.category})`);
      return;
    }
  }
  // ... existing resend.com dispatch unchanged
}
```

**Why inject at `sendEmail` rather than per-function**: there are dozens of existing call sites (order placed, approved, shipped, delivered, cancelled, payment received, gift recipient, …). Updating each one is N changes × N reviews. Updating the central sender is 1 change. Existing callers don't yet pass `uid + category` so they bypass the gate by default — safe for the deploy. As individual functions are reviewed, they opt their callers IN by passing the recipient's uid and category:

```typescript
// Before (passes through unchanged):
await sendEmail({ to, subject, html });

// After (gated — drops if user opted out of orderUpdates):
await sendEmail({ to, subject, html, uid: order.userId, category: 'orderUpdates' });
```

The mapping (which CF sends which category) is documented in `functions/src/lib/notificationPrefs.ts` header.

## What customers will notice

1. **Pasted URLs with apostrophes now work consistently.** `monk's-blend`, `darjeeling's-best`, anything else — gets redirected to the canonical form and the page loads. Markdown link-rendering edge cases also work because the canonical URL has no special characters.
2. **Returning visitors get a "Pick up where you left off" row on home** showing their last viewed teas, linking back to those pages.
3. **Users who opt out of marketing emails actually stop receiving them** as soon as the relevant CFs start passing `uid + category` to `sendEmail`. The gate is now active; the rollout is per-function-review.
