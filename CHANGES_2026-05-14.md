## 1. QR routing — customers scanning a tea-canister QR landed on `/offline.html`

**Files:** `vite.config.ts`

**Symptom:** Scanning the QR on any tea canister (e.g. "Keemun Panda")
opened Safari at `https://elecafe.ca/tea-profile/<cat>/<slug>` and the
service worker served the static `/offline.html` instead of the tea
profile, even with full bars.

**Root cause:** Two compounding mistakes in the Workbox config.
1. `navigateFallback: '/offline.html'`. For an SPA this should be the
   shell (`/index.html`) so React Router can render any client-side
   route. Pointing it at a dead-end page meant any navigation Workbox
   couldn't immediately fulfil got routed to "You're offline".
2. `StaleWhileRevalidate` on the navigation runtimeCaching rule. SWR
   races cache against network; first-time deep links have an empty
   cache, so any network hiccup (Cloud Function cold start, slow
   cellular) produced no response, fell through, and hit the offline
   page.

**Fix:**
- `navigateFallback` is now `/index.html` (the SPA shell). The shell is
  already precached via `globPatterns: '**/*.{js,css,html,...}'`.
- The navigation rule is now `NetworkFirst` with a 3 s timeout. Online
  visits get fresh HTML from `renderSeo`; slow networks fall back to
  the in-cache copy; truly-offline cache-misses fall through to the
  shell, where the existing `<OfflineBanner>` (driven by `useOnline`)
  surfaces connectivity state at the React layer.
- `navigateFallbackDenylist` now also excludes `/api/*`, `/sitemap.xml`,
  `/sw.js`, `/workbox-*.js`, and `/manifest.webmanifest`, so those
  cleanly 404 / pass through instead of getting the SPA shell.

## 2. Storefront — Availability filter produced an empty grid

**Files:** `src/lib/teaFilters.ts`

**Symptom:** On the Teas page, ticking both **In stock** and
**Out of stock** showed zero products with no explanation.

**Root cause:** `matchesTeaFilters` ran both checks unconditionally:
```ts
if (f.inStock && stock <= 0) return false;
if (f.outOfStock && stock > 0) return false;
```
With both flags set, every product is excluded by exactly one of those
two conditions — the intersection is empty by definition.

**Fix:** Treat both-checked as no constraint (the union of segments =
everything), matching what users actually expect. Same when neither is
checked.

## 3. Admin date-range filter — custom dates leaked into preset modes

**Files:**
- `src/app/pages/admin/AdminAnalytics.tsx`
- `src/app/pages/admin/AdminVerificationAnalytics.tsx`
- `src/app/pages/admin/AdminVisitsAnalytics.tsx`

**Symptom:** After using the "Custom" range once, switching back to a
preset like "Last 7 days" silently anchored the end of the range to
whatever date the admin had typed into the custom-end field. Today's
events / orders / visits disappeared from the dashboard.

**Root cause:** All three `presetToRange` / `getRange` helpers had:
```ts
const end = customEnd ?? new Date();
end.setHours(23, 59, 59, 999);
```
This used `customEnd` regardless of which preset was active **and**
mutated the caller's Date in place via `setHours`.

**Fix:** Split the function into two code paths. Custom mode uses
the user's typed dates (cloned, not mutated). Preset mode always
computes `end = new Date()` end-of-today, ignoring whatever the
custom inputs happen to hold.

## 4. Admin Products — Translate button shifted result fields when one source was empty

**File:** `src/app/pages/admin/AdminProducts.tsx`

**Symptom:** Pressing "Translate name & description" with only one of
the two English fields filled in produced wrong-target French. e.g.
admin filled `description` only → the translated description landed in
`nameFr` and `descriptionFr` stayed empty.

**Root cause:** `handleTranslate` ran `.filter(Boolean)` over the
sources before sending them to the API, then mapped results back
positionally to fixed targets (`nameFr`, `descriptionFr`). When one
source was empty, the filter dropped it but the targets didn't shift.

**Fix:** Adopted the source/target pair pattern from `handleTranslateAll`
in the same file — each pair survives the filter together, then results
are written back per-pair instead of by index.

## 5. Admin Products — Radix Select empty-string `value=""` quirk

**File:** `src/app/pages/admin/AdminProducts.tsx`

**Symptom:** The Caffeine and Antioxidants dropdowns sometimes
rendered without their placeholder text on first load.

**Root cause:** The form's `EMPTY` state initializes those fields as
`''`. Radix Select 2.x doesn't reliably render `<SelectValue placeholder>`
when the Root receives `value=""`.

**Fix:** Coerce `''` to `undefined` at the call site
(`value={form.caffeine || undefined}`). Radix never emits `''` back
through `onValueChange` (its `SelectItem` items forbid empty-string
values), so the round-trip stays consistent.

## 6. Admin Promotions — broken label↔input association on Discount Type

**Files:**
- `src/app/components/ui/Field.tsx` — added new `Field.Select` slot
- `src/app/pages/admin/AdminPromotions.tsx` — swapped raw `<select>`
  for `Field.Select`

**Symptom:** Clicking the "Discount Type" label didn't focus the
select. Screen readers couldn't announce the field's purpose via the
standard label-for relationship.

**Root cause:** A raw native `<select className="field">` was rendered
inside a `<Field>` wrapper but didn't pick up the Field context's
auto-generated `inputId`. The `<Field.Label>` therefore had
`htmlFor="field-discountType-…"` pointing at nothing.

**Fix:** Added a `Field.Select` slot to the `Field` primitive,
mirroring `Field.Input` and `Field.Textarea` — wires `id`,
`aria-describedby`, `aria-invalid`, `aria-required` from the Field
context. AdminPromotions now uses it.

## 7. Schema-fidelity audit (deep pass on `src/schemas/`)

Full audit of all 21 schema files against actual runtime usage. 14 gaps
found and closed. See `SCHEMA_AUDIT_2026-05-14.md` for the full report.

Headline data-loss bugs fixed:

- **`AdminProducts.handleAdd`** was writing a hand-built object literal
  that omitted the `blurhash` and `variantsAvailable` fields the
  validated `candidate` carried. Newly-created teas never persisted
  their image-pipeline metadata until the admin re-opened the product
  and re-saved. Now uses the validate-then-write pattern: `setDoc(ref, { ...parsed.data, ...serverFields })`.

- **`placeOrder` Cloud Function** dropped 3 of the 5 documented gift
  fields (`senderName`, `occasion`, `customOccasion`). The schema
  declared all 5 are mirrored to the top level so admin filters work
  without a data migration. Now all 5 persist.

- **All 9 transactional order emails** were calling `sendEmail({...})`
  without passing `uid + category: 'orderUpdates'`. The notification
  preferences gate was fully implemented on both sides but **never
  activated at the call site**. CASL/CAN-SPAM/GDPR-required toggles
  in `/account → notifications` had no effect. Now wired.

- **`AdminProducts.handleUpdate`** had the same dual-literal pattern
  as `handleAdd`. Refactored to map `parsed.data` undefined → null
  so admin can still clear Firestore fields by emptying the form
  input.

- **`migrateLegacyAnnouncementText`** existed in the schema but was
  never invoked. The Navbar comment claimed admin saves "auto-migrate
  server-side" — they didn't. Wired into `AdminSettings.handleSave`.

Schema-vs-reality drift cleanups:

- `userProfileSchema` had `isAdmin` and a nested `preferences` shape
  that no code ever wrote. Removed.
- `reviewSchema` declared `id`, `productId`, `title`, `images`,
  `verified`, `helpful`, and `updatedAt` — none exist in the real
  `/teas/{slug}/reviews/{userId}` subcollection docs. Rewritten to
  describe the actual 5 fields.
- `addressSchema.phone` required `min(10)` digits while
  `checkoutFormSchema` accepted 7. A phone the checkout writes
  succeeded would fail `validateAddress()` on round-trip. Aligned to
  the 7-digit heuristic.
- `notificationSchema`'s strict union for `customer_credit_admin_added`
  omitted `orderId` and `sourceType` even though the CF writes them.
  Added as optional fields.
- `categorySchema.labelFr` was declared but `useCategoriesRealtime`
  dropped it on the way out. Now surfaced; FR-locale customers can
  finally see French category labels (when admin writes them in
  Firestore).
- `AdminSettings.announcements` was typed inline; now uses the
  canonical `Announcement` type from the schema.
- `src/schemas/index.ts` barrel was silently missing 5 runtime-used
  schemas (`auth`, `checkout`, `announcement`, `userPreferences`,
  `firestoreTimestamp`). All now re-exported.
- `src/schemas/README.md` listed 11 schemas; the folder had 21.
  Rewritten to describe what's actually there, plus the
  validate-then-write rule.

## 8. Schema-fidelity audit — round 2 (collection-first pass)

Round 1 audited from the schemas side; round 2 ran from the Firestore
collections side (every write site → which schema models this?). Caught
7 more gaps (#15 – #21). Full per-gap detail in
`SCHEMA_AUDIT_2026-05-14.md`.

Highlights:

- **Two parallel type systems unified.** `src/types/firestore.ts` defined
  `OrderDoc`, `TeaDoc`, `UserDoc`, `OrderStatus`, etc. — a parallel
  type system that had silently drifted from `src/schemas/`. The drift
  caused a real customer-visible bug: `OrderStatus` in `firestore.ts`
  was missing `'ready_for_pickup'`, and the `OrderStatusTimeline`
  component (which imported from there) didn't include the status in
  its "Ready" step's `reachedBy` list. Pickup customers at status
  `ready_for_pickup` saw their timeline silently stuck at "Confirmed"
  even though their order was ready at the café counter. Fixed by
  deleting the parallel file, aliasing the names back from
  `src/types/index.ts` (which re-exports from schemas), and explicitly
  handling `'ready_for_pickup'` in the timeline's `reachedBy` lists.

- **`/settings/global` shape unified.** Three places disagreed on the
  doc's field set: `useSettings.SETTING_DEFAULTS` (client read),
  `AdminSettings.DEFAULTS` (admin write), and `firestore.ts SettingsDoc`
  (legacy partial type). Specifically the CF read `storeName`,
  `storeEmail`, `storeAddress`, `storePhone`, `storeWebsite`,
  `emailLogoUrl` from the doc — fields the client TypeScript type
  didn't know about. Created canonical `src/schemas/settings.schema.ts`,
  added the missing fields to `useSettings.SETTING_DEFAULTS`, and
  added admin-UI inputs for `emailLogoUrl` and `ogImageUrl` (both
  previously editable only via Firestore Console).

- **`orderSchema` gained `restored` + `restoredAt`.** Cloud Function's
  `restoreStockAndCredit` helper writes these markers but the schema
  didn't declare them — any `validateOrder()` round-trip would have
  stripped them silently.

- **Dead admin toggle `sendOrderEmails` wired up.** Admin had a
  "send order emails" toggle in `/admin/settings`. The toggle wrote
  to Firestore. The runtime never read it. Now wired into the CF's
  `sendEmail` as a global kill switch: when the toggle is off,
  every `category === 'orderUpdates'` send is suppressed. Use cases:
  pausing during a Resend incident, complying with a "do not send"
  demand, doing a manual data import without spamming customers.

After this round: every Firestore collection has either a schema whose
field set matches every write site, or an explicit "loose-shaped on
purpose" annotation. No parallel type systems remain.

## 9. Security hardening — Phase 4 (six critical fixes)

External audit flagged six items in the auth, checkout, and payment
surface. All addressed in this pass.

### #1 — Rate limit branded verification emails ✅

`functions/src/authEmails.ts` had an explicit TODO: any authenticated
user could spam the resend-verify button (or script the callable) to
inflate Resend cost / pollute their inbox. Added `enforceEmailRateLimit`
— a Firestore-backed ring-of-timestamps limiter using `/emailQuota/{key}`
docs and transactions. Wired into `sendBrandedVerifyEmail` at 5 sends
per hour per uid. Throws `resource-exhausted` with a `retryAfterMs`
payload so the client can render "try again in N minutes" instead of
an opaque toast.

### #2 — Close password-reset account enumeration (CWE-204) ✅

`sendBrandedPasswordReset` previously returned `{ registered: true | false }`,
letting the client render a differential modal ("we sent it" vs "no
account found, want to sign up?"). That doubled as an enumeration
oracle — an attacker could probe email lists and learn which were
registered.

Hardened response is uniform `{ ok: true }` regardless of whether the
email matched. Three layers:

1. **Uniform return shape.** Server swallows `auth/user-not-found`
   and returns success-shaped on both paths. Log row still records
   the unknown-email case for admin forensics.
2. **Timing equalisation.** `padResponseTo(startMs, 600)` floors the
   not-registered branch at the same wall-clock duration as the happy
   path. An attacker can't distinguish via response time.
3. **Per-email rate limit.** 3 sends per hour per normalised email,
   key=`pwreset:${email}`. Blocks both abuse and rate-limit-based
   enumeration (an attacker can't probe a list and infer registered
   status from which addresses hit the limit faster).

Client UI updated: `LoginPage` no longer renders `NoAccountFoundModal`
in the reset flow (component file preserved for future non-enumerating
uses). Single neutral "if an account exists for that email, we sent a
reset link" confirmation in all cases.

### #3 — Harden checkout retry logic ✅

Pre-fix `CheckoutPage` had `retriedThisOrderRef = useRef<boolean>(false)`
— a single-shot retry with a fixed 150ms wait. A verification flip
that took 300ms+ to propagate would fail twice and surface as a
generic "couldn't process your order" toast.

Hardened to:

- **Counter, not boolean.** `orderRetryCountRef = useRef<number>(0)`,
  capped at `MAX_AUTO_RETRIES = 2`. Counter (not boolean) so the cap
  is visible and bumping it later is a one-constant change.
- **Proportional backoff.** 200ms + attempt × 400ms (200 then 600ms).
  Long enough for Firebase Auth to propagate verification claim flips.
- **Broader retry coverage.** Added `permission-denied`,
  `unauthenticated`, `unavailable`, `deadline-exceeded` (and their
  `functions/` prefixed variants). Previously only `permission-denied`
  triggered the recovery path.
- **Exhausted-retries recovery.** When retries are spent and the token
  still won't accept, the toast now explicitly recommends sign-out
  / sign-in (the only known recovery for a stuck JWT cache) instead
  of a generic "contact support."

### #4 — Money-math regression coverage ✅

Pre-fix the promo discount math, credit math, and end-to-end order
total were inline in their respective hooks/pages. Three refactors
extracted pure functions and added tests:

1. **`calcPromoDiscount(opts)`** exported from `src/hooks/usePromoCode.ts`.
   The hook now calls the pure helper. Test file `promo-discount.test.ts`
   covers: percentage cap at 100%, maxDiscount cap on percentage promos
   (with insanely-large maxDiscount unable to push above subtotal),
   fixed > subtotal cap, defensive sanitisation of NaN/negative/Infinity,
   penny-precision rounding.
2. **`makeCreditConfig(settings)`** exported from
   `src/hooks/useCreditConfig.ts`. The hook is now a thin `useMemo`
   wrapper. Test file `credit-config.test.ts` covers the R3 Bug #7
   regression directly (dollarsPer1000=3 must give exact dollars, no
   lossy round-trip), defaults on null/empty settings, the
   `pointsToNextThreshold` zero-balance special case, defensive sanitisation,
   AND a parameterised matrix of `client formula matches server` across
   common rates and point amounts — pinning the rate-mismatch invariant
   that caused real "order rejected" failures pre-R3.
3. **`src/lib/orderMath.ts` (new module)** — canonical
   `calcOrderTotal(...)` + `orderArithmeticPassesRule(...)` for the
   cart→order arithmetic. Pre-extraction this formula was duplicated
   inline in CheckoutPage, CartSummary, AdminOrders, NotificationBell,
   and the CF (with small drift). The test file pins order-of-operations
   (promo BEFORE credit), clamping (never owe negative), the legacy
   `discount` alias, and the Firestore rule invariant on every realistic
   cart shape.

Coverage now meets the audit's bar: any silent financial bug would
flip these tests before reaching customers.

### #5 — Production env hard-check ✅

Pre-fix `src/lib/firebase.ts` warned about missing env vars in DEV
but silently booted in PROD with missing keys. A misconfigured deploy
would show a working-looking site that silently failed every Firebase
call. Hardened to:

- **DEV: warn loudly** (unchanged behaviour for fresh-clone DX).
- **PROD: hard `throw` at module load.** A missing
  `VITE_FIREBASE_API_KEY` / `_AUTH_DOMAIN` / `_PROJECT_ID` / `_APP_ID`
  prevents the SPA from booting at all — the misconfig surfaces during
  smoke-test, not from a customer email.
- **Soft-warning consolidated list** for optional-but-recommended
  vars (`VITE_FIREBASE_APP_CHECK_KEY`, `VITE_SENTRY_DSN`) — one log
  line at boot for deploy-review grep-ability.
- **`firebaseEnvPreflight()`** new exported helper returning
  `{ ok, missing, softMissing }`. Deploy smoke tests / monitoring
  pages can call it to verify the runtime config without trying to
  hit Firebase.

### #6 — eTransfer security answer customer visibility — INTENTIONAL ✅

Analysis confirms the rendering at `OrdersPage.tsx:304-330` is correct
per Interac eTransfer's classic flow: the customer (sender) MUST know
the security answer to set on their outgoing transfer; the café
(recipient) enters the same answer to accept the deposit. The answer
isn't a secret FROM the customer — it's a shared secret BETWEEN
customer and café, protecting funds in transit from third parties
who might intercept the eTransfer notification.

The more secure modern alternative is Interac Auto-Deposit (funds
land in the recipient's account with no security question at all).
Lever to remove customer-visible security answer entirely:

1. Café enables Auto-Deposit on their bank account.
2. Admin leaves `etransferPassword` setting BLANK in `/admin/settings`.
3. The conditional in `OrdersPage` already hides the "with security
   answer X" sentence when the field is empty.

Two documentation changes shipped:

- **Prominent comment in `OrdersPage.tsx`** explaining the security
  model and the auto-deposit alternative, so future maintainers don't
  "fix" this by moving the field out of the client UI (which would
  break the classic Interac flow).
- **Admin-facing guidance banner in `AdminSettings.tsx`** —
  "Security tip" callout in the Interac eTransfer section,
  recommending auto-deposit + blank security-answer field as the more
  secure posture. Hint text on the field itself updated to reflect
  this guidance.
